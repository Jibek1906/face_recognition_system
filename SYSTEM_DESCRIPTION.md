# Описание работы системы распознавания лиц

Данный документ содержит подробное описание архитектуры и алгоритмов работы системы.

## Структура проекта (обновлено)

Исторически проект был в виде плоского набора файлов `face_system/*.py`.
Чтобы привести к «реальной» структуре и **ничего не сломать**, добавлен пакет
`face_system/face_app/` с нормальным разбиением на слои.

Важно: старые файлы (`config.py`, `db.py`, `models.py`, `shared_state.py`,
`video_state.py`, `tracker.py`, `visit_manager.py`, `identity_manager.py`, …)
остались как **shim-обёртки** (re-export) и продолжают работать со старыми
импортами вида `from db import ...`.

### Карта модулей

- `face_app/core/config` — конфиг из `.env` (бывший `config.py`)
- `face_app/core/settings` — runtime-настройки из `settings.json` (бывший `settings_manager.py`)
- `face_app/db` — SQLAlchemy модели и сессии (бывшие `models.py`, `db.py`)
- `face_app/state` — shared state между потоками и API (бывшие `shared_state.py`, `video_state.py`)
- `face_app/vision/tracking` — трекер (бывший `tracker.py`)
- `face_app/domain/visits` — visit manager (бывший `visit_manager.py`)
- `face_app/domain/identities` — identity manager (бывший `identity_manager.py`)

Остальные большие модули (API/streaming/камера/модели CV) пока остаются в
`face_system/*.py` и будут переноситься следующими шагами.

## 1. Поток видео (Streaming)
Система поддерживает несколько источников видеопотока:
- **RTSP**: Основной поток с IP-камер (Reolink, Imou и др.). Используется библиотека OpenCV с бэкендом FFMPEG.
- **WebRTC**: Прямой поток из браузера для минимальной задержки.
- **Локальная камера**: USB или встроенные камеры (через `/dev/video0`).

### Как принимается поток:
За захват отвечает `CaptureThread`. Он работает в бесконечном цикле, постоянно считывая кадры ("фреймы") из источника. 
- **Оптимизация задержки (Zero Latency)**: Используется очередь типа LIFO (Last-In-First-Out) размером 1. Это гарантирует, что система обработки всегда берет *самый свежий* кадр, отбрасывая старые, если не успевает их обработать.
- **Буферизация**: Параметр `CAP_PROP_BUFFERSIZE` установлен в 1 для минимизации внутреннего буфера OpenCV.

## 2. Конвейер обработки (Pipeline)

### Шаг 1: Детекция (Detection)
В `DetectionThread` происходит первичный анализ кадра:
1. **Детекция тел**: Используется модель **MobileNetSSD** для нахождения силуэтов людей. Это позволяет "держать" человека в фокусе, даже если лицо временно не видно.
2. **Детекция лиц**: Используется библиотека **InsightFace** (модель `buffalo_l`). Она находит координаты лица, ключевые точки (глаза, нос, рот) и оценивает качество (четкость, освещенность).
3. **Сопоставление**: Система связывает найденное лицо с телом на основе перекрытия (IoU - Intersection over Union).

### ⚡ Оптимизация: Event-based gating (Alarm / FTP / Motion)
Чтобы поток меньше лагал и CPU не был постоянно загружен детекцией, добавлен режим **event-gating**:

- В обычном состоянии (нет событий) `DetectionThread` выполняет тяжелую детекцию **реже**
  (например 1 раз в 12 кадров), но при этом продолжает:
  - обновлять аннотированный кадр для HLS;
  - "состаривать" треки (чтобы не залипали боксы).
- Как только приходит внешний сигнал **alarm/event** (например камера отправила FTP snapshot),
  система переключается в "active" режим на несколько секунд и снова детектирует **каждый кадр**.

Источники event/alarm:
- `/ftp/process_image` (уже используется ftp_server.py) — автоматически маркирует событие;
- `/alarm/trigger` — легкий endpoint, который можно дергать из любого webhook/curl.

Настройки в `face_system/settings.json`:
- `event_gating_enabled`
- `event_gating_active_after_event_seconds`
- `event_gating_idle_processing_every_n_frames`
- `event_gating_active_processing_every_n_frames`
- `event_gating_activate_on_tracks`
- `event_gating_active_after_track_seconds`

### Шаг 2: Трекинг ("Иришки" / ID)
Каждому найденному объекту присваивается уникальный **Track ID** (то, что пользователь называет "Иришками").
- **Как они работают**: Трекер (`Tracker.py`) следит за перемещением бокса от кадра к кадру.
- **Метод сопоставления**:
    1. **Геометрия (IoU)**: Если бокс на новом кадре находится примерно там же, где был на предыдущем, это тот же ID.
    2. **Визуальное сходство (Embeddings)**: Если человек быстро переместился или пропал из кадра на секунду, система сравнивает его "цифровой отпечаток" (embedding) с историей активных треков.
- **Состояния трека**:
    - `TENTATIVE`: Объект только появился, система наблюдает.
    - `CONFIRMED`: Трек стабилен, он отображается в интерфейсе.
    - `LOST`: Человек временно скрылся (зашел за колонну). Система ждет его появления до 60 кадров.

### Шаг 3: Распознавание (Recognition)
Когда трек подтвержден, его лицо отправляется в `RecognitionThread`:
1. **Экстракция признаков**: Модель генерирует 512-мерный вектор (embedding) — математическое описание уникальных черт лица.
2. **Поиск в базе**: Вектор сравнивается со всеми векторами в базе данных (`IdentityManager`). Используется косинусное сходство (Cosine Similarity).
3. **Порог (Threshold)**: Если сходство выше установленного порога (например, 0.60), треку присваивается `Person ID` и имя.
4. **Автосоздание**: Если человек новый и его лицо четко видно на протяжении нескольких секунд, система автоматически создает для него новую запись в базе.

## 3. Передача данных и UI

### Где рисуются боксы?
Отрисовка происходит на стороне сервера в `DetectionThread`. Сервер берет текущие данные трекера и накладывает графику (рамки, имена, таймеры) прямо на кадр.

### Как данные попадают в интерфейс?
Система использует два канала:
1. **HLS Поток (Видео)**: Аннотированный кадр (с рамками) передается в `hls_streamer.py`, кодируется в формат `.m3u8` и отображается в плеере на сайте.
2. **WebSockets (`/ws/tracks`)**: Параллельно видеопотоку сервер отправляет JSON-пакеты. В них содержится:
    - Список всех, кто "в кадре" прямо сейчас.
    - Их координаты (для кликов или доп. анимаций).
    - Имена и текущий таймер посещения.
    - Время последнего обнаружения.

---

## 4. Резюме: Кто в кадре и откуда данные?
- **Источник**: Камера (RTSP URL).
- **Кто в кадре**: Список объектов `Track` в `SharedState`, у которых состояние `CONFIRMED`.
- **Передача**: 
    - Кадры -> HLS -> Браузер (Видео).
    - Данные трекера -> WebSocket -> Браузер (Текст/Метаданные).
- **Логика работы**: Постоянный цикл "Захват -> Детекция -> Трекинг -> Распознавание -> Отображение".

## 5. Alarm / FTP snapshots (фото по тревоге)

Камера может отправлять "snapshot" по тревоге на FTP сервер (`face_system/ftp_server.py`).

### Где появляются файлы
Загружаемые файлы сохраняются в:
`face_system/ftp_uploads/<camera_ip>/<camera_name>/<date>/...`

### Важно про формат файлов (.dat)
Некоторые камеры отправляют "фото" не как JPEG, а как **сырой H.265/HEVC поток** (часто с расширением `.dat`).
OpenCV такие файлы не читает напрямую.

В `ftp_server.py` добавлена автоматическая конвертация через `ffmpeg`:
- если пришёл `.jpg/.jpeg/.png` — используется как есть
- если пришёл `.dat` (или другой не-картинный файл) — берётся **первый кадр** через `ffmpeg -f hevc -frames:v 1` и далее обрабатывается как JPEG

### Debug: сохранять декодированные JPEG на диск
По умолчанию `ftp_server.py` удаляет входной файл после обработки.
Если нужно убедиться, что декодирование работает, включите сохранение JPEG:

```bash
export FTP_SAVE_JPEG=1
# опционально
export FTP_DEBUG_SAVE_DIR=/tmp/ftp_decoded
```

Тогда декодированные кадры будут сохраняться в `face_system/ftp_uploads/_decoded/` (или в `FTP_DEBUG_SAVE_DIR`).

### Как запустить FTP сервер
Запускать нужно через venv (там установлен `pyftpdlib`):

```bash
cd /var/www/face_recognition/face_system
./venv/bin/python ftp_server.py
```

Параметры FTP по умолчанию:
- host: `0.0.0.0`
- port: `2121`
- user: `ftpuser`
- password: `123456` (в отладочном режиме пароль игнорируется для `ftpuser`)
